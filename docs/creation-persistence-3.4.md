# Etapa 3.4 — Equipo, archivos y persistencia

Base publicada: 49680ea46c1d3d74bdd0de8ed9710aab6d6fb571 (CI correcto). Inspección: creación 3.1–3.3, esquemas de Fighter, equipo 2.2, integración Laboratorio/Coliseo, API de registros, migraciones y pruebas web.

La ficha nativa conserva nombre, procedencia, atributos, entrenamientos, umbrales, rasgos, posesiones y propiedad, decisiones, semilla, dados y versiones. El equipo de laboratorio y el perfil `creation-resistance-4-v1` son campos separados: elegirlos nunca cambia la ficha canónica ni concede Dominios. La Resistencia canónica continúa nula; el jugador debe elegir expresamente el perfil técnico antes de preparar combate. La interacción de ceguera con combate sigue pendiente: esas fichas se conservan y exportan, sin inventar modificadores.

El editor compartido admite arma principal/reserva, manos, armas de dos manos, armadura, consumibles y Energía finita de ensayo. Presenta inventario y manos sin atribuir el equipo adicional a posesiones iniciales. No se agregan presupuestos, peso ni capacidad sin regla documentada. Laboratorio y Coliseo reciben el mismo Fighter derivado de la ficha; cambiar equipo no altera atributos ni entrenamiento. Reiniciar el escenario cargado conserva el personaje creado. Entrar al Coliseo con una ficha preparada abre su configuración, sin restaurar automáticamente una carrera ajena; las carreras guardadas siguen cargables.

Tres vías: mantener en sessionStorage sin servidor (también al llevar la ficha a combate), guardar una copia en la biblioteca compartida cuando está configurada, y descargar/importar JSON nativo. Hay exportación legible Markdown. Importar valida tamaño, formato, esquema, versiones y SHA-256; además reproduce toda la ficha desde entrada y catálogo para detectar datos o cronologías inconsistentes. Se importa como copia, sin sobrescribir registros. El servidor aplica la misma validación, sesión, origen y control de revisiones existentes.

La prueba de ida y vuelta detectó una dependencia del orden de claves de los puntos libres al serializar JSON canónico. Se corrigió ordenando esas asignaciones; `core02-creation-v2` identifica el nuevo orden de salida. El espacio de semillas original `core02-creation-v1` permanece congelado: las tiradas no cambian por esta corrección. El informe v1 permanece histórico; `reports/creation-audit-v2.json` registra otras 10000 semillas y repeticiones exactas con la salida actual.

Se agrega el tipo de registro `creation` y la migración idempotente `004_created_characters.sql`, que amplía el CHECK sin cambiar datos existentes. El despliegue con base de datos debe aplicar las migraciones mediante `npm run migrate` usando su DATABASE_URL. Este entorno no tiene DATABASE_URL ni `.env.local`; no se ejecutó una migración sobre producción. La migración y el flujo de guardar/cargar una ficha completa con equipo se verificaron en la base de integración de `test:web`, incluyendo rechazo de datos manipulados.

Pruebas: 115 tests, 10000 generaciones/repeticiones, tipos, lint, formato, build y web. E2E: seis rutas de creación, equipo de dos manos, descarga real, importación exacta y rechazo de corrupción sin perder la ficha, sesión sin servidor, traslado a ambos modos y responsive. Capturas en `reports/creation-ui/`, incluidas `native-equipment.png` y su versión móvil; captura de equipo revisada visualmente.

Con esta etapa termina la implementación del plan atómico original dentro de la cobertura y los pendientes reglamentarios declarados. Continúa la cola de ampliaciones de combate solicitada después; todavía no se declara terminado ese lote ni se pide QA final.
